# Panther P1A validation — pure-AOSP decoupling audit

Status: **PASS / host-read-only evidence**

Purpose: determine whether the pinned Pixel 7 Android-17 support-generation references can be used as bounded external inputs for a SableOS AOSP-based bring-up without adopting GrapheneOS as the operating-system substrate.

## Frozen inputs

- device: Pixel 7 (`panther`)
- stock build: `CP2A.260705.006`
- Android release: 17 / SDK 37
- SELinux: Enforcing
- active stock slot during audit: `_b`
- signed GrapheneOS reference-manifest default base: `android-17.0.0_r1`
- AOSP `android17-release` manifest head observed during P0: `29ace668ae756c7b8917c57abb440f6518844b0c`
- AOSP Rust toolchain: `1.93.1`
- `adevtool`: `5019450d9235c48a987250c890e346b416f8dfd4`
- `vendor_state`: `d69d029d7fe3745049e80ad64ad1967a9cac8e5f`
- `device_google_pantah-kernels_6.1`: `b3fd241e7f8b3283c864b3e6e464f853defb5997`

All three external pins revalidated exactly before the audit. The physical Pixel 7 remained on the same build/slot and no root, reboot, flash, Android workspace creation, product build, or Sable source mutation occurred.

The pinned `adevtool` build-ID-to-AOSP-tag index does not contain Android-17 Pixel build mappings. Therefore **P1A does not claim that `CP2A.260705.006` maps exactly to `android-17.0.0_r1`**. What is proven is that the signed external reference manifest uses `android-17.0.0_r1` as its default AOSP base while the Pixel vendor-generation configuration targets the July stock build. P1B/V0-HOST must freeze the exact resolved AOSP project manifest actually built and treat Pixel vendor/firmware provenance separately.

## Product-base result

The `adevtool` Pixel product path inherits standard AOSP product definitions for system, system_ext, product, vendor, emulated storage, generic ramdisk, Trusty, virtualization, dynamic partitions and Virtual A/B infrastructure. The pure-AOSP product base is therefore usable as the starting point for a Sable-specific Pixel generation adapter.

The recursive make include closure for Panther is bounded to six files:

```text
config/mk/google_devices/device/panther/device.mk
config/mk/google_devices/platform/gs201/device.mk
config/mk/google_devices/platform/gs201/product-common.mk
config/mk/google_devices/common/device-common-gs201-plus.mk
config/mk/google_devices/common/product-common.mk
config/mk/google_devices/common/device-common.mk
```

## GrapheneOS-only product hooks

Exactly six GrapheneOS-specific hook lines were found inside that active include closure:

```text
GosOverlay
init.gs201.grapheneos.rc
init.pixel.grapheneos.rc
CarrierConfig2 + GosTelephonyProviderOverlay + GosTelephonyOverlay
gos-dhdutil
restrict-pixel-health-association
```

These hooks are explicit product/init additions rather than proof that the full Pixel-generation engine requires the GrapheneOS platform.

The generator source contains a small number of GrapheneOS-specific code paths, mainly for GrapheneOS image recognition/download handling, generated-file attribution, and GrapheneOS-specific source/image cases. These must be reviewed during generation, but they do not justify treating the GrapheneOS OS tree as the Sable substrate.

Decision:

```text
PANTHER_P1A_GRAPHENEOS_SUBSTRATE=NO
PANTHER_P1A_ADEVTOOL_BLIND_IMPORT=NO
PANTHER_P1A_SABLE_ADEVTOOL_ADAPTER=REQUIRED
```

The Sable adapter should remove/replace GrapheneOS-only product hooks before the first pure-AOSP product build while keeping the stock-derived Pixel vendor/device material generated by the audited tooling.

## Generated vendor reference classification

The generated Panther skeleton itself contained only two textual matches in the coarse GrapheneOS scan: the generated-by attribution URL and an unrelated carrier filename containing the substring `legos`. The vendor specification similarly had only the latter filename match.

This is evidence that GrapheneOS product coupling is concentrated primarily in the shared product configuration, not broadly embedded throughout the generated Panther proprietary-file inventory.

`vendor_state/panther.json` is **reference-only**, not a stock payload. It contains GrapheneOS application/package state such as Auditor, Vanadium and `app.grapheneos` entries. It must not be copied into a Sable product or treated as the authoritative stock package set.

## Kernel result

The pinned Pantah 6.1 kernel-prebuilt reference contains 341 non-git files and includes `grapheneos/Image.lz4`. A `grapheneos/dtbo` file was not present at the probed path. This is a path/layout observation only; it is not evidence that Panther lacks a DTBO image. DTBO/kernel packaging must be resolved from the generated product/build graph during P1B/V0-HOST rather than inferred from this single reference path.

## Health / power result

The generated Panther product references:

- `android.hardware.health-service.gs201`
- `android.hardware.health-service.gs201__2`
- recovery health service support
- modern Android Health NDK interfaces
- Pixel power and power-stats services

Therefore the bramble HIDL 2.1 bridge is **not assumed reusable** on Android 17 / Panther.

Portable Sable semantics remain authoritative:

```text
Android-17 Panther Health adapter
        -> existing Sable PowerState semantics
        -> frozen Sable power API semantics
```

The next service-port gate should qualify the actual AIDL Health callback/client interface on the built Panther baseline before implementing an adapter.

## Security / provenance policy

- base platform remains AOSP Android 17;
- the exact built AOSP project set must be frozen as a resolved manifest during P1B/V0-HOST;
- Pixel July stock vendor/firmware provenance is tracked separately from the AOSP platform project snapshot;
- GrapheneOS remains a reference/security source, not the OS substrate;
- `adevtool` output must be generated from pinned stock inputs and reviewed/diffed;
- GrapheneOS-only hooks are removed or replaced explicitly;
- stock proprietary/vendor/kernel/firmware provenance is recorded independently;
- no global AOSP Rust uplift is needed: Android 17 already provides Rust 1.93.1;
- Android APK/ART/PackageManager compatibility remains part of the baseline.
