# Titan 2 engineering operator performance contract — ai-g732

**Binding from 2026-10-28 for newly delivered SableOS host scripts and substantial revisions.** This is a performance and correctness gate within the original five-phase stock/Android16 investigation; no source patch, build, device contact, flash, or firmware changes authorized.

## Why this contract exists

The owner-measured Phase3A2 V1 `correlate3a2.py` processed a SHA-sealed stock dataset with 41,002,821 DEX invoke entries but used one Python core. During one real host run PID 3734918 remained near 99.9% of one CPU with only ~37–39 MiB RSS; at >17 minutes its DEX invoke compressed-input byte position was 34.1% (165,806,080/485,839,284). That is **active progress**, not a deadlock, but the package's prior 100k-row synthetic test was **insufficient to predict full-host throughput**. Disk read counters were not proof of useful rows processed. The running process is not to be modified or terminated by this policy. The V1 output, if it completes and its seal checks, remains valid.

Code diagnosis of V1 (reviewed 2026-10-28):
- `scan_csv` constructs a new `dict(zip(...))` for every input row;
- each DEX invocation triggers `text_domains(caller)`, `text_domains(target)`, `text_domains(path)`: each `text_domains` executes up to **eight regular-expression searches**; row-specific literal extra tokens can add more scans;
- `gzip.open(..., compresslevel=4)` writes themed results on the same Python core;
- there are no periodic progress markers during the full scan; no multi-process workers and no representative host-scale benchmark receipt.

These are source-based bottleneck candidates, **not a measured CPU flamegraph**. Profile before claiming which consumes most cycles.

## Mandatory qualification before publishing the next ZIP or script

1. **Inspect the target machine constraints at run time**: `os.sched_getaffinity(0)`, effective cgroup CPU quotas where available, `os.cpu_count()`, Linux `MemAvailable`, cgroup memory limit and available scratch-disk capacity. Never hard-code ai-g732's CPU count or assume all 64 GiB physical RAM is free. Publish `HOST_CAPACITY.json` including CPU affinity, quota, physical/available memory, chosen workers and batch/scratch budget. No subscriber/device data.
2. **Profile representative real workload** before algorithm selection. For large stock-file scans, use an admitted SHA-pinned, deterministic bounded sample of **at least 1,000,000 real DEX invoke rows** from the existing 41M corpus where resources permit. Include a mix of matched and unmatched rows, long descriptors, multiple dex members and representative native/config data. Keep input provenance. Benchmark the exact old and new operations on comparable inputs; do not extrapolate from mock data alone.
3. **Use a fast serial correctness reference first.** Avoid per-row dict allocations where named fields can be indexed once by validated header, avoid checking artifact paths with eight regexes 41M times if the path is constant per JAR, and precompute combined fast-reject regex/substring probes before domain-specific classification. Profile the actual improvements. Do not drop `DEX_INVOKES` records or silently narrow stock discovery.
4. **Exploit parallelism when it materially improves throughput.** Large independent work should support `--workers auto|N` with a safe serial fallback. Auto should derive from *effective* affinity/cgroup CPU availability; initial cap `min(16, max(1, floor(0.75 * effective_cores)))`. Use bounded batching/queues or independent deterministic shards; memory-backed aggregation must be bounded. For gzip, plan around its sequential input stream: use one reader with bounded batches or verified decompressed seekable shards, never have N workers independently reread all 41M entries. Support extra worker processes only if their measured speedup outweighs IPC/decompression overhead.
5. **Respect RAM and scratch budgets.** The host has 64 GiB physical RAM, not an unlimited allocation. Default to at most **50% of current MemAvailable**, and reserve at least **16 GiB or 25% of physical RAM, whichever is larger**, for OS/other builds. Bound queues and cap per-worker memory; preserve streaming for large inputs. Halt/hold safely on scratch exhaustion rather than filling the filesystem.
6. **Benchmark workers and memory together**: measure single-process and `--workers 4` and `--workers 8` where effective cores allow, plus actual selected auto count. Use wall time (`/usr/bin/time -v` or Python perf_counter), CPU time, max RSS, input/output bytes, throughput (rows/s and MB/s), compressed output, scratch peak, process count, total device contact=NO. Keep all validation results in a sealed `PERFORMANCE.json` and `PERFORMANCE_VALIDATION.md`. Use tests that reproduce input distribution and include millions of rows when feasible; label synthetic separately.
7. **Correctness parity is mandatory** across serial and parallel on the same fixed real sample: same total input row counts; exact source SHA seals; same classifications, owner counts, boundary counts, output contents after canonical sorting when order is not part of the contract, and deterministic final report hashes excluding explicitly declared timing/worker metadata. Reject missing/duplicated/out-of-order records or incomplete chunks.
8. **Progress and cancellation**: emit a one-line progress heartbeat at least every 30 seconds on long work: stage, records checked and expected, matched rows, bytes input if knowable, elapsed time, process count, and peak RSS; do not display invented percent complete. Handle SIGINT/SIGTERM with a fail-closed partial-work cleanup, never publish an incomplete final `RESULT.json`.
9. **Performance acceptance is machine-measured**: don't label full 41M corpus performance `PASS` until the new operator has been benchmarked on ai-g732 under the current storage/CPU load. Prefer a >=1.5x speedup at four workers on compute-heavy representative data; if no speedup, profile and justify serial mode. A faster version must not waive SHA verification, parser bounds, privacy handling, or unresolved-boundary semantics. If unable to benchmark, mark `PERFORMANCE_UNQUALIFIED_HOST_RUN_PENDING`, do not claim scalable performance.
10. **Publish evidence and exit codes:** every substantial script package includes `README.md`, `ENGINEERING_REVIEW.md`, `TEST_LOG.txt`, `VALIDATION_LOG.txt`, `PERFORMANCE.json` (explicit synthetic/host source), `SHA256SUMS.txt`, deterministic tests, and dry-run syntax validation. Record command line, exact input hashes, machine/cgroup capacity, row count, worker count, elapsed and peak resources. Final publication must be atomic and fail closed.
